# Watchlist — 8-Week Beginner Programming Track

**Date:** 2026-07-29
**Status:** Approved
**Mentor:** Ahmad Alhaich
**Student:** no computer-science background, ~15–20 h/week, Lebanon

## Purpose

Take a student with zero programming background to the point where he has built,
understood, and deployed a small full-stack web application in eight weeks — and
give the mentor a continuous, honest signal about whether the student is capable
and disciplined enough to continue.

Two outputs, equally important:

1. **For the student:** a real deployed app, a public GitHub history, and working
   knowledge of HTML, CSS, JavaScript, TypeScript, Express, and a database.
2. **For the mentor:** evidence. Roughly 30 pull requests, a daily learning log,
   and a hard go/no-go checkpoint at week 4.

## Non-Goals

- Teaching computer-science theory (algorithms, complexity, data structures beyond
  arrays and objects).
- Touching the Mehemte or TICKIT codebases. This project is deliberately unrelated.
- Producing a production-quality application. The app is a teaching vehicle.
- Covering React or any frontend framework. Plain DOM first; frameworks come after
  these eight weeks.
- Building authentication as a hard requirement. It is a marked stretch goal.

## Decisions

| Decision | Choice | Reason |
|---|---|---|
| Language | JavaScript → TypeScript | One language front to back; no second ecosystem to learn. Direct on-ramp to the mentor's Node/TS stack without using its code. |
| First output medium | Browser (HTML/CSS) | A beginner needs visible results. A live URL in week 1 is the strongest retention lever available. |
| Project topic | Movie & series watchlist | Universal CRUD shape (list → filter → detail → create/delete → accounts); a free public API exists (TMDB); the content is his own taste, so he cares. |
| Backend | Node + Express + TypeScript | Matches mentor's stack; same language as the frontend half. |
| Database | Prisma + SQLite | Prisma is easier for a beginner than raw SQL and is what the mentor uses. SQLite needs no install; the switch to MySQL is a datasource change. |
| Monitoring | Pull request per task | Protected `main` forces review. Gives a per-task audit trail of what he wrote and when. |
| Repo visibility | Public | GitHub Pages (the week-1 live URL) requires a public repo on a free plan, and a public history is the student's portfolio. Consequence: no secret may ever be committed — which is why the key lesson is scheduled in M5–M6. |
| Doc language | Simple English | All real resources are English; reading them is itself a required skill. Every term is defined in `GLOSSARY.md`. |
| AI/tutorial policy | Allowed, but must be explained | Banning is unenforceable. Requiring explanation measures the thing that actually matters. |

## Repository Structure

One repository, `watchlist`, owned by the mentor. The student is a collaborator
with write access; `main` is protected.

```
README.md                        what this is, how to run it
LEARNING.md                      student's daily log, ~3 lines per day
CONTRIBUTING.md                  the working rules: branches, commits, PRs, the AI policy
.gitignore
docs/
  CURRICULUM.md                  all 8 milestones, every task, checkboxes
  SETUP.md                       Node, VS Code, Git, GitHub, first commit
  GLOSSARY.md                    plain-English definitions of every term used
  MENTOR.md                      mentor-only: weekly checks, red flags, review checklist
week01/ … week05/                small standalone exercises, ~5 per week
app/                             the capstone; grows every week
.github/
  pull_request_template.md
```

`week01/…week05/` hold throwaway exercises that build muscle memory. `app/` is the
single artifact that grows for eight weeks. Keeping them separate means a broken
exercise never breaks the app, and the app's git history reads as one clean story.

## Milestones

Each milestone is one week. Each contains 3–5 tasks. Each task is one branch, one
pull request, one review. Every milestone ends with something that visibly runs.

### M1 — Setup and first web page (week 1)
Install Node, VS Code, Git. Create a GitHub account. Learn HTML structure and
enough CSS to lay out a card grid.
**Ships:** static watchlist page with 6 hardcoded movie cards, deployed to GitHub
Pages at a public URL.
**Why this shape:** a live URL in week 1 is worth more than any amount of theory.

### M2 — JavaScript fundamentals (week 2)
Variables, types, functions, `if`/`else`, loops, arrays. Exercises in `week02/`.
**Ships:** the same page, but cards are generated by looping over a JavaScript
array instead of being written by hand.

### M3 — DOM and events (week 3)
Selecting elements, listening for clicks and form submissions, changing the page
from code.
**Ships:** add a movie via a form, delete a movie, mark watched/unwatched, filter
by watched state, search by title. All state in memory; refresh loses everything.

### M4 — Objects, JSON, and localStorage (week 4)
Objects, nested data, `JSON.stringify`/`parse`, `localStorage`. Splitting one long
file into named functions.
**Ships:** the list survives a page refresh. First review that judges *structure*,
not only whether it works.
**Gate:** see "Week 4 Gate" below.

### M5 — Async and real data (week 5)
`fetch`, promises, `async`/`await`, HTTP status codes, JSON responses.
**Ships:** search TMDB by title and add a real movie with its real poster, plus
loading and error states. The API key lives in a gitignored config file — the
first, deliberately incomplete, lesson on secrets.

### M6 — TypeScript and his own backend (week 6)
npm, `package.json`, `tsc`, types, interfaces. A small Express server.
**Ships:** `GET /movies` and `POST /movies` on his own server; the frontend talks
to it instead of holding data itself. The TMDB key moves server-side — the
complete secrets lesson, and the reason the backend exists.

### M7 — Database (week 7)
Schemas, migrations, Prisma Client, the difference between memory and storage.
**Ships:** movies persist in SQLite through Prisma; restarting the server no
longer loses data.

### M8 — Deploy and polish (week 8)
Environment variables in production, build steps, a README someone else can follow.
**Ships:** frontend and backend both deployed and talking to each other over the
internet; README with screenshots; a written retrospective.

### Stretch — Accounts (not required)
Signup and login with bcrypt-hashed passwords and a JWT, so each user has their
own list. Weeks 6–8 are the hard cliff for a beginner at 15 h/week. Auth is
explicitly optional so that a slip does not turn into an unfinished project: he
can deploy a working single-list app and still have finished.

## The Week 4 Gate

At the end of week 4 the mentor makes an explicit go/no-go decision.

**Go** — M1–M4 are merged, he can explain his own code in PR descriptions, and he
has committed on 4 or more days in most weeks. Continue to M5.

**No-go** — repeat weeks 3–4 with different exercises rather than starting the
backend. The backend half compounds on DOM and data fluency; without those it
becomes copy-paste, and copy-paste teaches nothing and signals nothing.

This gate is written into `CURRICULUM.md` so the student knows it exists from day
one. A checkpoint he can see is a motivator; a secret one is a trap.

## Workflow Rules (`CONTRIBUTING.md`)

1. One task, one branch: `week03/add-delete-button`.
2. Small commits, present tense: `add delete button to movie card`.
3. Open a PR when the task works. Never push to `main`.
4. The PR description answers three questions: what did you change, why, and what
   confused you.
5. Write in `LEARNING.md` every day you work — three lines is enough.
6. **AI and tutorials are allowed.** But every PR must explain, in your own words,
   what each change does and why. If you cannot explain a line, delete it.
7. Being stuck for 30 minutes is normal. Being stuck for 2 hours without asking is
   not — ask, and say what you already tried.

Rule 6 is the core of the design. It reframes the unenforceable question ("did he
cheat?") as the enforceable and more useful one ("can he explain it?").

## Mentor Monitoring (`MENTOR.md`)

**Weekly, ~20 minutes:**
- Read the week's PR descriptions before reading any code.
- Skim `LEARNING.md` for the week. Empty log = disengaged, regardless of code.
- Check the commit calendar: 4+ days of small commits is healthy.
- Leave at least one comment that asks *why*, not just *what*.

**Red flags:**
- Large, flawless PRs with vague descriptions → generated, not understood.
- One giant commit on Sunday night → cramming, not learning.
- `LEARNING.md` untouched for a week.
- Never asks a question. A real beginner has questions every week.
- Same conceptual mistake three weeks running after being corrected.

**Green flags:**
- Asks specific questions with what he already tried.
- PR descriptions mention something that confused him.
- Voluntarily goes back and cleans up earlier code.
- Ships something small that was not on the task list.

## Deliverables of This Project

The scaffold to be built, in order:

1. `docs/CURRICULUM.md` — 8 milestones, ~30 tasks, each with a branch name,
   acceptance criteria, and a link to one or two learning resources.
2. `docs/SETUP.md` — installation and first-commit walkthrough, step by step,
   assuming no prior knowledge.
3. `docs/GLOSSARY.md` — every term used anywhere in the docs, in plain English.
4. `docs/MENTOR.md` — the monitoring guide above, expanded per week.
5. `CONTRIBUTING.md` — the workflow rules above.
6. `README.md` — what the project is, how to run it, where to start.
7. `LEARNING.md` — with a filled-in example entry so the format is obvious.
8. `.github/pull_request_template.md` — prompting the three PR questions.
9. `app/` — week-1 starter files (`index.html`, `styles.css`) with the first task
   left deliberately unfinished, so his first PR is real work.
10. `week01/` — the first five exercises.

GitHub repository creation, collaborator invitation, and branch protection are
mentor actions to be confirmed before execution, not performed automatically.

## Risks

| Risk | Mitigation |
|---|---|
| He quits in week 2 when novelty fades | Week 1 ends with a live public URL; every milestone ships something visible |
| Weeks 6–8 are too steep | Auth demoted to stretch; week 4 gate catches the problem before the cliff |
| Tutorial copy-paste with no understanding | Rule 6 (explain every line) plus PR descriptions that ask what confused him |
| Mentor stops reviewing, student loses motivation | Weekly review capped at ~20 minutes; PR descriptions read before code |
| TMDB API key committed to a public repo | Key gitignored in M5, moved server-side in M6 as an explicit lesson |
| English resources block him | `GLOSSARY.md`; simple sentences; every task links a specific resource, not "google it" |
